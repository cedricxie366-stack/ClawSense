# P1 延迟续修与完整播报检查

日期：2026-10-22。Host **0.2.0-preview.9**／Android **0.3.9-live-playback-preview**（versionCode13）。对应[现行计划](../产品演进路线与执行计划.md)，延续[10月21日候选](p1-ready-2026-10-21.md)。P1仍未整阶段签核，公共发布与招募暂缓。

## 本人听到的截断与测试修正

本人反馈：“你目前的测试我都听过，完全无法完整的播出一句语音。”此前自动停止检查会在声音开始约400ms后注入生成的“停”，所以解释火山的句子会刻意被打断。这类检查只能证明停止和不恢复，不能证明正常播报完整。此前没有提前说清测试的听觉影响。

另外发现了一个独立的测试缺陷：恢复问答只等到 Host 的 `completed`（生成完成）便断开连接，未等待手机播放剩余音频。**生成完毕不等于播报完毕。**旧停止／不恢复证据仍保留，旧“恢复回答14”不应扩大解释成该句完整听验通过。

当前修改：

- 手机以实际 `AudioTrack.playbackHeadPosition` 和已写入的PCM帧数判断播放结束，代替固定150ms收尾猜测；处理32位无符号计数回绕，停止／换代重置计数。播放器未消耗完尾音时保持播放状态与回声隔离，停止按钮仍立即暂停和清空。
- 完整回复检查不注入停止，不开麦克风或相机。先等模型生成完成，再等手机播放头消耗全部音频，最后断开。
- 自动停止检查及完整回复检查仅将本次测试的播放器增益设为0，结束释放并恢复测试标志；不更改系统音量。真人听验继续单独标注，不将静音检查当作听感通过。
- 恢复问答也等待整个音频播完。客户端关闭事件先于服务端异步清理的测试竞争另已修正，检查等待服务端实际设置空闲计时器后再触发，未放宽生产断开逻辑。

## 实际完整播报结果

当前OPPO Find X2／PDEM10、Android13，安装0.3.9。实际本地模型回答：

> 会议安排在明天下午四点，预算五万元，方案周六交付。

收到并写入 **144000个24kHz音频帧，共6秒**，播放头最终也为144000；没有注入“停”，麦克风帧数0，测试播放器静音。文字发出后5.674秒开始写音频，9.663秒生成结束，11.826秒播放结束。**生成结束后仍需播放约2.16秒**，旧测试的提前断开会丢掉这一段。上述证明实际手机消费了完整PCM，不替代真人自然度与每个字读音的听验；首音等待本身也不能写成已达短答3秒目标。

## 冷准备与停止优化

1. TTS用短句的一帧真实声音完成预热，并显式关闭预热流；正式回答的文本、采样、音色与流式输出参数保持。交替模型对照中，同一正式测试句的四份PCM完全相同，首段约184–198ms，没有将省下的预热等待直接转移到该句首音。隔离模型结果不能等同手机冷启动。
2. 播报即将开始而短口令识别器闲置时，并行做有上限的短预热；合并重复准备，不为每个音节启动新工作，也不在后台持续空转。最近已有实际识别则复用。
3. 在至少8逻辑CPU的Mac上，将整句／短口令复核限定为4个CPU线程；其它机器保留2个，流式识别线程数保持。停止仍要求确切口令，不将“银”“听”强行解释成“停”。

本轮先连接小米13 Ultra，后检测到换为OPPO；两台手机的样本分开记录，不混算收益：

曾尝试延后首次短口令复核、固定识别窗口及调整系统线程QoS。没有得到足以采用的稳定收益；固定窗口试验还出现检查失败，期间有手机切换，不能臆定单一原因。这些实验未纳入候选。更短预热最初的两线程十轮检查仍有两次超过一秒，也保留为失败范围，不只报告最快数字。
