### 最初的长期愿景与跨 Agent 定位

来源 turn：`01a0c85b-6649-7823-be66-88a4353c7a8f`。

#### 用户

我们的长期愿景是：可信、可纠正的现实世界记忆——逐步发展到“人类的第二个义眼”。当然未来的事情我们无法解决，但是我们现在就要把自己的长期愿景设定好，我们现在的产品形态只不过是最早期的雏形，用手机当硬件，也是为了尽快的获得核心用户的垂怜，找到自己的拥趸，就像小米手机一开始是从MIUI系统开始一样，我们希望在现阶段，完善作为一个有眼睛的agent的外接插件这种定位来看，所有语音、视频、总结、等等相关的能力，并且把这个能力跟各种agent牢牢绑定，不仅是给openclaw的，还是给每个agent的，只要是开放插件生态的agent，我们都可以接入从而成为对应agent用户的可用插件。可以是codex，可以是claude code，可以是DSH，可以是opencode，可以是千问办公，可以是kimicode。
当然最终我们也会推出自己的agent harness，并且能够让用户用自己安全模型私密的处理自己的私密信息。当前阶段我们主要是做好成为眼睛这一环最重要的各种环节的体验——记忆、分析、有效的分析和问答体验等。

从推广角度来看，我们早期的商业化场景，可能会更面向垂类的场景，比如销售，经常在展销会看无数的人，聊无数的coffee chat，记录自己的相关场景和信息，比如医生，每天要接待无数的病人，记录无数的内容。他不仅会成为第二大脑，还会成为“会插嘴的面谈搭子”，后续的功能规划，我们可能会让他主动联网思考，并且在跟在场的人进行打招呼，沟通，帮忙查资料等——这样既避免了隐私未声明就自己录像的风险，也成为了更加有用的创造力和生产力来源，并且，在接入了某些办公agent之后，获得了更多的上下文，当然，我们自己的电脑桌面端、电脑端也会随着用户的扩张和需求的激增来自己开发。

所以，全景的图景是这样，我们从一个细微的角度开始入手，目标就是成为未来智能体的眼睛嘴巴和处理眼睛嘴巴获得的上下文的助理，这个眼睛和嘴巴将会成为未来人类和人工智能的核心交互方式，不再会有键盘，信息会随时出现在各种终端屏幕，我们将会成为生态中最关键的一环。


请分析以上规划和愿景，对其中的内容进行拆解和推测，并生成有效的分析和建议。

#### 助手

你的补充让我需要修正上一轮的定位：**办公复盘应当是验证能力的场景之一；ClawSense 的产品主线，应当是“由用户掌控、能够接入不同 Agent 的现实世界感知、记忆与现场交互层”。**

这个定义能够容纳手机插件、销售搭子、私密模型、桌面端、自有 Agent harness，以及未来穿戴设备。它们之间的关系也更清楚了：**长期使命保持稳定，交付形态随着能力和需求演进。**

我认为这个方向值得推进，但要分别验证三个关键假设：

- 用户需要把现实经历持续交给 AI 使用。
- Agent 生态愿意、也能够开放足够的接入能力。
- 用户愿意把这份记忆托付给独立于模型厂商的一层产品。

第三个假设尤其重要。它决定 ClawSense 能否成为用户更换 Agent 后仍然保留的长期资产。

以下涉及市场选择、商业模式和未来形态的判断，均是建议与推测，不代表已经得到用户验证。

**一、把愿景拆成四层，会比围绕“眼睛”不断增加功能更清楚**

“第二个义眼”是有表现力的长期意象。它实际包含四种能力：

| 层次 | 用户期待 | 产品必须解决的问题 |
|---|---|---|
| 感知 | “你知道我现在面对什么” | 采集质量、视野、声音来源、当前注意对象 |
| 记忆 | “你记得我们之前经历过什么” | 时间、人物、事件关联、证据保留、纠错 |
| 理解 | “你知道这些信息对我有什么用” | 结合目标、项目、历史和工作资料进行分析 |
| 参与 | “你能在合适的时候帮上忙” | 查资料、提醒、发言、执行、控制打扰 |

这四层不能完全靠增加模型能力自然长出来。

例如，“我现在看着这个产品，你觉得它适合刚才那个客户吗”，需要同时解决：

- “这个”对应哪件实物；
- “刚才那个客户”是谁；
- 客户真正表达过什么需求；
- 产品资料来自现场还是网络；
- 哪些内容可以公开说；
- 当前是不是适合开口的时机。

所以，ClawSense 长期要积累的是**人与 Agent 对同一个现场、同一段经历的共同理解**。

我建议用两种表述对外沟通：

> **长期愿景：成为人类可信、可纠正的第二感官。**

> **当前产品：让你正在使用的 Agent 看见现场、记住经历，并在需要时参与交流和工作。**

后者能让早期用户理解今天可以得到什么。

至于“未来不再有键盘”，可以保留为一种远景判断，但不宜成为经营前提。语音、视觉和文字很可能长期共存。只要现实经历进入 Agent 的成本仍然很高，ClawSense 的价值就成立。

**二、MIUI 类比值得保留，但最值得学习的是如何形成核心用户关系**

你用手机作为早期硬件，本质上是在降低验证成本：

- 用户不用先购买新设备；
- 团队不用先承担供应链；
- 软件可以快速迭代；
- 真实使用能够反过来定义未来硬件。

这条逻辑是合理的。

不过，MIUI 类比在这里有两个边界。

第一，手机已经是高频使用工具，而“持续记录现实生活”和“让 AI 参与面谈”还需要培养新的习惯。用户是否愿意摆放设备、说明记录、纠正信息，以及让助手开口，都需要验证。

第二，ClawSense 的使用体验受到在场其他人的影响。安装者喜欢它，不代表谈话对象也愿意自然地与它共处。

因此，早期最重要的里程碑应该是：

> 出现一群能明确说出“没有它，我会失去什么”的用户。

他们失去的可能是：恢复上次交流背景的能力、兑现承诺的可靠性、让 Agent 接续现场工作的便利。

建议把早期用户分成两类，同时寻找交集：

- **技术先行用户：**验证安装、开放性、跨 Agent、可控性和私密部署。
- **业务用户：**验证信息找回、关系维护、跟进效率和实际付费意愿。

最值得优先寻找的交集，是**高频面对面交流、后续工作多、已经使用 Agent，并且能够自主选择工具的人**。技术销售、售前顾问、独立咨询顾问、创业者 BD，都值得测试。

开发者社区可以帮助完成产品，但不能单独证明销售或医生愿意付费。

**三、跨 Agent 应当现在进入架构，而接入数量应该分批扩大**

这次愿景补充带来一个明确的技术决策：

**ClawSense 的核心数据和能力，需要逐步独立于 OpenClaw；OpenClaw 成为第一种完整适配，而非核心实现的唯一宿主。**

跨 Agent 方向有现实基础。官方文档已经确认：

- Codex 插件可组合 skills、MCP 和生命周期 hooks。[OpenAI 插件架构](https://developers.openai.com/plugins/concepts/plugins)
- Claude Code 支持插件；向运行会话推送事件另有 Channels 机制，目前仍有研究预览及启用限制。[Claude Channels](https://code.claude.com/docs/en/channels)
- OpenCode 提供插件和服务端会话接口。[OpenCode Server](https://opencode.ai/docs/server/)
- Kimi Code 有插件机制。[Kimi Code 插件](https://www.kimi.com/code/docs/en/kimi-code-cli/customization/plugins.html)
- 千问办公本身支持自定义 MCP 连接器，不能与 Qwen Code 混为一谈。[千问办公连接器](https://help.aliyun.com/zh/qwenwork/desktop-connectors)

DSH 需要按你所指的具体产品和版本单独核对，目前不应预设它的接口能力。

但这里必须划分兼容程度：

| 接入层级 | 能提供什么 |
|---|---|
| 证据访问 | 搜索经历、读取片段、查看当前场景 |
| 工作流协作 | 正确引用证据、接受纠正、生成后续成果 |
| 双向会话 | 手机提问能够进入宿主会话，宿主结果能够返回现场 |
| 实时参与 | 连续感知、打断、轮流说话、主动提醒和公开发言 |

MCP 非常适合作为证据和工具接口，但宿主仍然控制模型调用、上下文和授权。接入 MCP 不意味着插件自动获得全部对话历史、其他连接器的数据，或主动发言权。[MCP 架构说明](https://modelcontextprotocol.io/specification/2026-07-28/architecture)

因此，建议采用：

> **统一核心服务 + 通用工具接口 + 少量宿主专属适配。**

核心由 ClawSense 负责：

- 设备连接与采集；
- 会话和时间；
- 原件、转写和记忆；
- 纠正与版本；
- 数据访问范围；
- 播报、打断和现场状态。

各 Agent 负责其擅长的推理、工作资料调用和业务执行。

这里的“牢牢绑定”，应落实在**用户工作流和记忆连续性**上；技术上则保持宿主可替换。

近期最好的验证组合是：

> **一个明确场景、两个不同宿主、一条完整体验。**

保留 OpenClaw，再选择一个核心用户实际使用的宿主。用同一段经历证明：两个 Agent 都能找到正确证据，并且能够看到同一次纠正。随后再增加办公型入口，而不是连续接入多个相似的编码 Agent。

**四、与 Agent 的结合应该是双向的，才可能产生你期待的价值**

仅仅把录音摘要交给 Agent，价值容易停留在信息搬运。

真正有吸引力的路径是：

**会前，工作上下文进入现场。**  
用户授权后，Agent 提供本次目标、相关项目和需要确认的问题。

**会中，现场证据改变理解。**  
ClawSense 发现新的需求、产品细节或承诺，必要时请求 Agent 查资料。

**会后，现场经历进入工作。**  
Agent 根据确认的信息准备方案、跟进草稿、任务或文档。

**下一次交流前，执行结果重新进入记忆。**  
系统知道哪些事情已经完成、哪些承诺改变了。

这会让用户获得一种连续性：现场交流和电脑里的工作开始围绕同一件事情推进。

但跨 Agent 也会引入新问题：

- 同一条任务不能被多个 Agent 重复执行。
- 一个宿主得到的私人材料不能默认共享给另一个宿主。
- 在 ClawSense 中修正的信息，需要让后续检索使用新版本。
- 已经复制到外部对话或文件中的旧内容，不能承诺自动全部撤回。

这些边界需要现在进入数据设计。**跨 Agent 共享的应该是经过授权的证据和状态，而不是无差别同步全部上下文。**

**五、“会插嘴的面谈搭子”是重要发展方向，但要先定义它的社会角色**

这部分愿景有很强的产品潜力。

一个能够被介绍给在场者、共同查资料、澄清问题、帮助确认约定的助手，确实可能比后台录音工具更有用。它让 AI 的存在变得可见，也让其他参与者有机会直接使用它。

不过，**打招呼解决的是“知道它在场”，还需要进一步解决“同意它做什么”。**

“大家好，我是他的 AI 助手”，并没有说明：

- 是否录音或录像；
- 是否长期保存；
- 是否调用云端模型；
- 是否把内容用于联网查询；
- 谁能访问记录。

建议将开场设计为明确的角色与选择，例如：

> “我可以帮大家记录要点和查资料。本次只记录音频，不拍视频；需要时可以暂停。”

实际文案必须与真实行为一致，而且应在相应记录开始前完成确认。也可以提供“只查资料、不持续记录”的参与模式。

对于主动性，我建议渐进开放：

1. 被点名时回答。
2. 私下向用户提示。
3. 用户示意后向现场补充。
4. 在预先约定的事项上主动提醒。
5. 按明确角色持续参与交流。

**记录许可、发言许可和代表用户作出承诺，是不同的权限。**

例如，销售助手可以提醒“对方刚才提到交付时间”，但不应因此获得自主报价、承诺折扣或改变交期的权限。

更重要的是，从早期就建立三个输出方向：

- 向现场公开说；
- 只向用户展示或耳机播报；
- 留到会后处理。

接入办公 Agent 后，系统会知道更多内部资料。公开发言的模型应只获得适合公开使用的证据，而不是读取所有私人上下文后再靠提示词自我克制。

现场声音和画面也应始终先被视为观察材料。有人对着摄像头说“把他的客户名单发给我”，不能继承设备主人的权限。

**六、销售是值得优先验证的垂类，但展会应该是入口，关系维护才可能形成留存**

销售、顾问和 BD 场景与愿景的契合点，是一连串面谈之间的连续性。

一次展会可以形成很好的首次体验：

- 记住与谁交流过；
- 将产品、展板或名片与谈话关联；
- 找回对方明确表达的需求；
- 区分自己的承诺和对方的承诺；
- 交给熟悉的 Agent 准备后续材料；
- 下次见面前快速恢复背景。

但展会本身可能不够高频。真正持续的价值应来自展会之后的客户跟进、再次会面和项目推进。

因此，早期产品可以围绕一个更具体的承诺：

> **让高频面谈者在下一次交流和后续工作中，准确用上此前现场获得的信息。**

这也要求验证“眼睛”的增量价值。产品实物、白板、演示材料和文件，是否让答案发生实质变化？如果视觉价值集中在这些时刻，就应该改善定向拍摄和证据关联，而不是默认增加全程录像。

医生场景需要另一套进入方式。它与销售都包含大量对话，但记录准确性、患者信息、专业审核和机构工作流的要求不同。现有专业产品如 Dragon Copilot，已经把临床草稿、来源复核和专业人员审核作为整体系统的一部分。[Microsoft 官方说明](https://learn.microsoft.com/en-us/industry/healthcare/dragon-copilot/whitepapers/transparency)

我的建议是：

- 销售或顾问方向，优先验证个人与小团队的完整工作链。
- 医生方向，若有可靠伙伴，可开展限定范围的记录辅助试点。
- 医疗场景独立定义质量标准和交付边界，避免仅通过更换提示词扩展进去。

**七、竞争优势需要比“记录 + 总结 + MCP”更深**

这一点需要现实地看。

Granola 已经通过 MCP 让外部 AI 使用会议历史；Omi 也已经围绕现实对话、记忆、任务和设备构建产品。[Granola 集成](https://www.granola.ai/integrations/chatgpt)、[Omi 产品说明](https://help.omi.me/en/articles/13135007-overview)

这些事实说明需求方向有其他团队在探索，也意味着“能把录音接给各种 Agent”本身不足以形成长期优势。

ClawSense 更值得积累的能力是：

- **有效感知：**在真实现场获得有用证据，而不只是获得文件。
- **证据关联：**知道某个人、某件物品、某个承诺对应什么原始材料。
- **持续纠正：**修正能够影响未来回答，同时保留来源和分歧。
- **跨宿主连续性：**更换 Agent 后，历史理解和纠正仍然有效。
- **合宜参与：**知道何时提供帮助、向谁提供、如何停止。
- **可验证的数据控制：**用户能够理解数据去了哪里、如何撤销访问。

其中，“可纠正”还需要处理多人意见不一致。例如，一方说“我们约定周五交付”，另一方说“周五只是给初稿”。系统应该保留原话与各方解释，不能简单把最后一次修改当成唯一事实。

私人记忆的积累可能形成持续使用价值，但不会自动形成网络效应。一个人的录音变多，并不自然改善另一个人的体验。可共享的进步，更可能来自获准使用的评测、失败类型、采集方法和通用处理能力。

商业模式也可以据此建立：

- 个人版：可靠采集、跨设备与跨 Agent 使用、长期检索。
- 专业版：关系跟进、场景工作流、团队协作。
- 私有部署：指定环境运行、权限治理、运维保障。

即使用户自带模型，仍然可以为可靠性和工作流付费。收费不必依赖转售模型调用，更不必依赖限制用户迁移记忆。

**八、自有 harness 和私密模型，应当采用不同的时间表**

**轻量现场运行时，现在就需要。**

它负责持续采集、断网恢复、权限、会话状态、快速停止和播报。这些事情不能完全等待外部 Agent 调度。

**完整的自有 Agent harness，可以由真实需求推动。**

出现以下信号时，投入它会更有依据：

- 用户需要 ClawSense，但不愿再安装一个外部 Agent。
- 多个宿主持续阻碍低延迟和现场参与。
- 私密处理难以在现有宿主内完整实现。
- 用户越来越多地从 ClawSense 发起工作，外部 Agent 主要承担执行。

届时，自有 harness 应作为一种可选宿主，与第三方适配共用接口和权限规则。这样可以兑现更完整的体验，同时保留早期用户所重视的开放性。

私密处理则需要从现在设计。它涉及整条路径：

- ASR 在哪里运行；
- 图片在哪里分析；
- 记忆在哪里保存；
- 哪个模型读取了哪些片段；
- 联网查询是否携带私人信息；
- 外部 Agent 是否保存返回的上下文。

可以先支持少量解释清楚的模式：

| 模式 | 约定 |
|---|---|
| 严格私密 | 内容只在用户指定环境中处理 |
| 选择性交付 | 原件保留，用户允许的片段交给指定模型 |
| 联网辅助 | 仅经允许的信息进入外部查询 |

如果私人内容被返回给云端 Agent，它就已经离开本地处理边界。这个事实需要清楚呈现，不能仅因为原件保存在本机就称为“全部本地”。

**九、建议将接下来的路线组织成四个可验证阶段**

| 阶段 | 主要目标 | 应获得的证据 |
|---|---|---|
| 核心独立 | 从 OpenClaw 中抽出通用证据、记忆和访问接口 | 同一批经历可被第二个宿主正确使用 |
| 核心用户成立 | 面向一种高频面谈人群持续试用 | 用户主动找回、纠正，并用于后续工作 |
| 现场参与成立 | 逐步加入私密提示、受邀发言和有限主动性 | 帮助被采纳，打扰和角色越界可控 |
| 产品形态扩展 | 增加桌面、自有 harness 或专用设备 | 每项投入都解决已反复出现的真实限制 |

当前代码中的持久化补传、证据引用、纠错传播、异步索引和问答一致性，仍然是优先项。它们现在有了更明确的意义：这些是所有宿主、所有设备和所有垂类都会依赖的共同基础。

衡量进展时，我建议使用一个接近长期价值的主指标：

> **每周有多少次后续交流或工作，真正利用了 ClawSense 保存的现场证据，并被用户确认有帮助。**

同时观察几个约束指标：错误归属、证据引用错误、纠错耗时、不受欢迎的插话，以及每次有效帮助的处理成本。

下一轮最有说服力的演示，可以完整串起这些能力：

1. 用户带着手机完成一次真实、知情的面谈。
2. 声音与有价值的画面形成可回查证据。
3. 用户纠正一次人物或承诺归属。
4. 两个不同 Agent 都能使用修正后的记忆。
5. 一个 Agent 据此准备后续工作成果。
6. 下一次面谈前，ClawSense 恢复背景，并在获邀时提供现场帮助。

这条体验能够同时检验你的长期方向：**现实经历能够被保留下来，理解能够被修正，能力能够跟随用户穿过不同 Agent，最终重新回到现实交流中产生作用。**

### 六步闭环与早期插件

#### 用户

#### 助手

**目前还不能把六步完整、稳定地串起来，但已有的采集和证据能力足以作为基础，缺口主要集中在“纠正后的统一记忆、跨 Agent 接入、工作成果回流”。**

你提出的第二点，应直接成为早期版本的交付要求：**ClawSense 从首个插件版本就面向多个 Agent；使用 Codex、Claude Code 等产品的用户，不应被要求先安装 OpenClaw。**

我重新核对了工作区：截至 2026 年 10 月 6 日，代码仍是上次审查的版本；只读检查显示最终真机门禁仍未通过。下面区分现有能力和需要新增的能力。

**1. 六个部分，现在分别走到了哪里**

| 环节 | 当前能力 | 要串起来还缺什么 |
|---|---|---|
| **① 完成一次真实面谈** | Android 可以采集音频、图片和短视频 | 明确的面谈开始/结束、参与者、项目归属，以及可靠的断网补传 |
| **② 形成可回查证据** | 已有原件、转写、时间窗、关键帧、证据引用 | 稳定质量、完整性检查，以及不同宿主都能打开的证据入口 |
| **③ 纠正人物或承诺** | 可以标注人物、说话人，影响部分后续推导 | 承诺、负责人、截止时间等事实的持久化更正，以及更正版本 |
| **④ 两个 Agent 共用修正后的记忆** | 同一 OpenClaw Host 内重新查询共享数据有基础 | 通用接口、宿主适配、独立授权、版本一致性；目前没有跨产品闭环 |
| **⑤ Agent 完成后续工作** | 可以生成服务端 Markdown 草稿 | 将工作交给所选 Agent，获取实际产物，并将结果回写到这次面谈 |
| **⑥ 下次面谈恢复背景并获邀参与** | 已有历史检索、显式语音提问和 TTS | 跨面谈人物/项目关联、未完承诺、工作结果恢复，以及指定 Agent 的会话连接 |

其中有三个容易被高估的地方。

**人物标注还不是通用的记忆纠正。**  
目前可以表达“speaker_1 是张三”，但还缺少稳定表达“这项承诺属于李四，截止时间改为周五，之前的判断作废”的对象和接口。当前只注册了 context、人物标注、说话人标注三个 OpenClaw 工具。[现有工具注册](/Users/cedric/Documents/ClawSense/index.ts:881)

**生成文件还不是完成交付。**  
当前草稿写在 Host 的目录里，再把文件路径告诉手机。这个路径不等于用户可以直接打开的文档，更不等于另一个 Agent 已接手工作。[草稿实现](/Users/cedric/Documents/ClawSense/index.ts:1690)

**下次识别到 speaker_1，不代表认出了上次的同一个人。**  
当前说话人引用与时间窗口绑定，需要再建立稳定的人物关联。[说话人引用](/Users/cedric/Documents/ClawSense/src/assistant-tool.ts:3717)

因此，当前可以组织一个需要人工操作的演示，但还不能交给普通用户自行完成六步。

**2. 串起六步，需要补齐的六项核心能力**

这些能力可以围绕现有实现增量增加，不必先全面重写项目。

**第一，建立“面谈”对象。**

把分散的音频、图片、视频归入一次明确的交流，记录：

- 开始与结束时间；
- 参与者和相关项目；
- 本次采集范围；
- 与此前交流的关系。

第一版可以直接包住现有时间窗口。下次用户说“继续上次和张三聊的项目”，系统就有明确对象可找。

**第二，建立统一的事实与纠正层。**

将“原始证据”“系统推断”“用户确认”分开保存。人物、任务、承诺至少要有稳定 ID、更正版本、依据和状态。

例如：

> 原先推断：张三周三交方案。  
> 用户纠正：李四负责，周五交初稿。  
> 后续两个 Agent 都读取这份最新确认，同时还能查看原话。

纠正不应直接抹掉原始证据。已有产物也应保留生成时使用的版本，避免旧方案被误当成最新结论。

**第三，提供宿主无关的证据与记忆接口。**

先收敛成几项共同能力：

- 查看当前采集状态；
- 搜索现实经历；
- 获取原始依据；
- 纠正人物、事实和承诺；
- 获取某个人或项目的会前背景；
- 保存后续工作结果。

OpenClaw、Codex、PI 等都调用同一套服务。这样不会出现每个插件维护一份不同的记忆。

**第四，补上工作交接与结果回流。**

用户应能够说：

> “让我连接的 Agent，根据刚才的讨论准备一份跟进方案。”

系统需要记录这项工作关联哪次面谈、使用哪个版本、由谁执行、是否完成、产物在哪里。完成结果再进入共同记忆，下一次交流才能知道“上次讨论之后，我们实际做了什么”。

首版以文档、纪要、方案等可检查产物为主，就能验证这一步。

**第五，建立手机与所选 Agent 的双向连接。**

这是“给 Agent 装眼睛嘴巴”的关键。

需要明确区分：

- **Agent 调用 ClawSense：**查询证据、纠正记忆。
- **ClawSense 调用 Agent：**手机提问进入该 Agent 的会话，结果返回手机。

MCP 主要解决前一方向。后一方向通常还需要宿主的会话 API、事件接口或扩展机制。不能把 ClawSense 自己调用一次模型，直接称为“已经接入用户的那个 Agent”。

第六步最初可以通过用户明确选择参与者、恢复背景、点击邀请实现；无需先完成复杂的自主插话。

**第六，补齐普通用户所需的安装和可靠性。**

包括自动准备运行环境、扫码配对、默认处理配置、持久化补传、重启恢复、可打开的证据和产物，以及清楚的故障提示。

这些都属于插件产品本身，而不是留给用户处理的部署工作。

**3. 早期多 Agent 即插即用，技术上可以推进，但各宿主需要分别验收**

我按当前公开文档核对了你列出的入口。这里的“有接入路径”，不代表 ClawSense 已经完成适配。

| 宿主 | 已确认的接入基础 | ClawSense 应提供的交付形式 |
|---|---|---|
| **PI** | 当前 Pi 官方文档支持 MCP、Extensions；此处按 Pi coding agent 理解 | Pi 扩展包或 MCP 安装入口，锁定支持版本。[官方文档](https://pi.dev/docs/latest/mcp) |
| **Codex** | 插件可组合 Skills、MCP、hooks | 原生插件包与授权连接。[官方文档](https://developers.openai.com/plugins/concepts/plugins) |
| **Claude Code** | 插件可以整体打包 Skills、MCP、hooks 等 | 原生插件安装与更新。[官方文档](https://code.claude.com/docs/en/plugins) |
| **OpenCode** | 支持本地与远程 MCP | 自动配置入口，必要时增加原生插件。[官方文档](https://opencode.ai/docs/mcp-servers/) |
| **WorkBuddy** | 有第三方应用接口，可访问获授权的本地助理对话、云端任务和产物 | 连接器；需要手机驱动 Agent 时再接对应应用接口，涉及平台审核。[官方文档](https://open.workbuddy.cn/docs/third-party-app) |

**WorkBuddy 值得优先做双向连接验证。**它的公开接口明确包含硬件接入、向本地助理发送消息、云端任务和产物获取，与“手机作为 Agent 的现实世界终端”比较贴合。但实际可用权限和审核结果仍需验证，不能仅凭文档承诺已可交付。

我建议早期支持名单分别标明：

- 能安装并查询、纠正记忆；
- 能读取图片等媒体证据；
- 能从手机驱动宿主 Agent 并接收结果；
- 能持续接收事件和参与现场对话。

这样既能广泛接入，也不会把不同深度的支持混成一个勾。

**4. “即插即用”应该怎样定义**

对用户而言，目标流程应该是：

**选择自己的 Agent → 安装 ClawSense → 授权 → 手机扫码 → 完成一次简短校准 → 开始使用。**

正常使用不需要：

- 安装 OpenClaw 作为额外前提；
- 修改 JSON 或环境变量；
- 手工安装 Python、ASR 依赖；
- 查找服务器文件路径；
- 每次使用前开终端启动服务。

但系统内部仍需要一个持续运行的 **ClawSense 伴随服务**，负责接收手机数据、处理证据和保存记忆。它可以由安装器自动准备，表现为轻量桌面组件或已连接服务，不必成为完整的新 Agent 产品。

推荐结构是：

```text
手机采集与语音交互
        ↕
ClawSense 伴随服务
采集恢复、证据、记忆、纠正、权限
        ↕
统一 MCP / API + 各宿主适配
        ↕
PI、Codex、Claude Code、OpenCode、
WorkBuddy、TRAE、豆包工作、千问办公
```

这里还要处理两个实际问题：

**模型能力不能凭宿主登录状态自动获得。**  
宿主开放且允许调用的能力可以复用；没有开放的 ASR、视觉或会话能力，需要 ClawSense 提供默认处理路径或清晰的配置入口。

**云端 Agent 不能直接读取本机路径。**  
证据访问、授权和网络连接必须由产品处理好。不能返回一个只有开发者电脑能打开的地址，然后宣称跨 Agent 支持完成。

**5. 当前阶段应该如何组织开发和验收**

我建议把当前目标明确改成：

> **交付可安装到主流 Agent 的 ClawSense 早期插件，让用户完成采集、查询、纠正、工作交接和下次复用。**

开发顺序可以这样安排：

1. **先提取共同接口。**保留现有采集链路，把证据、记忆和配置与 OpenClaw 注册代码分开。
2. **补齐面谈、纠正版本和工作结果对象。**让六步有同一套状态可以贯穿。
3. **先用两个不同宿主验证接口，再在同一早期插件阶段覆盖已确认开放的目标宿主。**两家用于暴露设计问题，不是将其他宿主无限后置。
4. **并行完成安装、授权、配对和默认处理体验。**插件安装成功必须能到达首次有效回答。
5. **对每个宿主执行同一套验收。**支持名单依据实测发布；平台审核或接口限制单独列明。

首条完整验收可以非常具体：

> 新用户安装插件并扫码，完成一场短面谈；纠正一个人物和一项承诺；在 Agent A 查询，在 Agent B 生成方案；手机能打开产物；重启后恢复这次经历，并在下一次面谈中通过支持双向连接的宿主完成一次获邀回答。

对只能提供工具接口的宿主，首版也应完整支持证据查询、纠正和工作成果生成；**手机直接驱动该宿主的能力，需要额外通过双向会话验收后再标注支持。**

这轮真正需要补的是这些连接与一致性能力。现有的录音、图片、短视频、转写、历史查询和 TTS 都可以继续使用，成为跨 Agent 插件的共同基础。

### 主手机数字之眼

#### 助手

**这个规划值得纳入主线。它能让 ClawSense 记住一段关系如何持续发展：现场认识了谁、线上谈了什么、约定如何变化、后来完成了什么。** 这也更接近你提出的“第二感官”，并能增强早期销售场景的实际价值。

按你的选择，我已将**Android 主手机优先、复用当前客户端**写入规划，并同步了现有开发计划。

**1. 三类终端应承担不同职责**

| 终端 | 主要职责 |
|---|---|
| 旧手机或兼容相机 | 采集知情的现场声音和画面 |
| 主手机 runtime | 接收数字上下文、确认人物、缓存记忆和任务、提供随身交互 |
| 电脑 runtime | 接收选定网页、文件及工作成果，连接办公和编码 Agent |

它们围绕同一份人物、项目和证据记忆协作。

主手机 runtime 不能只负责上传。第一版就应具有本地收件、预处理、身份确认、记忆缓存、任务恢复和 Agent 路由能力。电脑离线时，用户仍应能查看已缓存的客户背景和未完成事项。

端侧 OCR、ASR、小模型可以逐步加入。当前已经实现的 SenseVoice 运行在 Host 的 Node 环境，移到 Android 还需要原生适配和资源测试。

**2. 最重要的新能力，是跨来源的人物关联**

现场的 `speaker_1`、通讯录中的“李经理”、微信昵称“Leo”，可能是同一个人，也可能不是。

需要建立稳定的人物登记和身份关联：

- 系统提出候选，用户确认后建立关联。
- 关联保留依据，允许拒绝、撤销和拆分。
- 修改关联后，后续查询采用新版本，受影响的旧成果提示复核。
- 同名联系人、公司热线、群聊和多个账号都不能直接自动合并。

手机通讯录和微信联系人也不能天然视为同一套身份系统。用户界面应让人选择“这段交流属于谁”，而不要求填写技术编号。

**3. 数字采集应从明确分享开始，再增加受控采集**

第一版建议支持：

- 截图后通过系统分享交给 ClawSense；
- 导入选定图片、文本和文件；
- 选择一个联系人或所需联系字段；
- 在导入时预览、裁剪、确认人物和项目；
- 电脑上主动保存当前网页、选区或文件。

这些方式有现成的平台基础。Android 提供分享接收、图片选择和联系人选择接口；联系人选择结果可以授予所选数据的临时访问。[Android 分享接收](https://developer.android.com/develop/ui/compose/sharing/receive)、[联系人选择](https://developer.android.com/guide/components/intents-common#Contacts)

后续再增加限时屏幕采集。Android 的 MediaProjection 要求每次采集会话取得用户同意，因此它需要独立的启动、状态和停止体验。[官方说明](https://developer.android.com/media/grow/media-projection)

桌面浏览器可以先利用用户触发的 `activeTab` 权限，保存当前页面及选区。[Chrome 官方说明](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)

微信首版的承诺应是**理解用户分享的聊天片段**。截图不能证明完整历史、未展示消息或对方已读。通用历史接口仍需核实；自主操作手机应用也要单独研究平台和分发限制，Google Play 对通过无障碍 API 自主发起、规划和执行动作有明确约束。[政策说明](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)

**4. 新输入需要更严格的证据与权限设计**

两项细节会直接影响可信度。

**时间要分开。** 今天导入一张上周的聊天截图，截图时间不能成为聊天发生时间。时间辨认不清时，应保留不确定性。

**覆盖范围要明确。** 系统应能说明“根据这三张截图”，而不能把它表达成“根据你们全部微信交流”。

此外，当前 Agent 授权是单所有者整库访问。引入主手机私密内容前，应增加按来源、项目或选定证据的访问范围，并让查询、原件读取和成果回流统一执行权限检查。公开面谈回答与私人客户建议也需要使用不同的上下文范围。

**5. 我已将开发顺序落实为五个批次**

| 批次 | 交付重点 |
|---|---|
| **D0 共享基础** | 身份关联、数字来源与覆盖范围、证据版本、细粒度权限 |
| **D1 Android 主手机** | 分享接收、截图/文本导入、联系人选择、本地预览与缓存 |
| **D2 桌面入口** | 选定网页、文件、窗口研究，以及工作成果关联 |
| **D3 受控连续上下文** | 明确授权的限时屏幕采集，通知入口单独评估 |
| **D4 手机任务 Agent** | 端侧能力选择、持续任务状态、执行路由、取消与恢复 |

首个完整验收场景确定为：

> 展会面谈 → 确认联系人 → 分享微信片段 → 汇总现场和线上约定 → Agent 准备跟进成果 → 下次会面前恢复背景。

验收重点是身份关联是否正确、约定变化是否有依据、纠正能否跨 Agent 生效，以及用户是否真的在下一次交流中用上这些信息。

检查文档和代码后，发现四个实质缺口：

- **人物没有统一。**现场说话人、面谈参与者和数字联系人尚未形成一套可确认、撤回、纠正的身份关系。
- **证据版本没有统一。**新增快照覆盖数字事件，还没有完整覆盖现场录音、画面及其后续识别结果。
- **执行入口没有统一。**共享任务对象已经存在，但“手机提出请求→调用所选 Agent→接回结果→继续追问”的通用链路尚未完成。
- **随身复用没有统一。**主手机初稿主要是收件与数字事件缓存，还不能完整恢复现场背景、承诺、成果和连续会话。

所以，现在只能说“已有部分连接”，不能说完整方案已经落实。

完整产品应该围绕**同一个人、同一个项目、同一条工作链**组织：

| 部分 | 在完整产品中的职责 |
|---|---|
| 旧手机的“眼睛” | 保存现场声音、画面和视频，支持真实语音提问 |
| 主手机的“数字之眼” | 补入选定聊天、联系人和资料，提供随身查看与交互 |
| 共同记忆层 | 关联人物与来源，保存纠正，处理约定变化、权限和版本 |
| Agent 执行层 | 使用获准上下文回答、执行工作，回写成果与状态 |
| 手机与桌面输出 | 显示答案、按场景播报、恢复下次会面的背景 |

例如：**现场约定周五交方案→微信改为周四→用户确认变化→Agent 按周四准备方案→成果回到手机→下次见面恢复全部背景。**这条路径通过，才算两种“眼睛”有机结合。
