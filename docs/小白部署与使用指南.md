# ClawSense 小白部署与使用指南

这份文档面向两类人：

- 想把旧 Android 手机变成 ClawSense 感知节点的人
- 想把 ClawSense 接到自己 OpenClaw 服务端上的人

这不是“产品官网文案”，而是一份基于真实跑通过程整理出来的操作指南。  
能跑通的部分我会明确写“已验证”，还没做成正式发布态的部分我会明确写“当前限制”。

## 0. 先说推荐用法

ClawSense 当前推荐运行在：

- **由原生多模态大模型驱动的 OpenClaw**

推荐原因很简单：

- 图片、音频和关键窗口的日回顾，更依赖多模态理解
- ClawSense 现在的主分析路径，是“先整理成事件窗口，再让 OpenClaw 当前主模型分析关键窗口”
- `runtime STT` 现在是兜底，不再是主路径

也就是说：

- 推荐：多模态 OpenClaw
- 兼容：非多模态 OpenClaw + runtime STT 降级

## 0.1 当前项目节点

可以把 ClawSense 现在的状态理解成 3 个连续阶段：

1. `Phase 1` 已经初步完成
   - Android 端和 OpenClaw 主机端已联通
   - 音频上传已验证
   - 图片上传已验证
   - 心跳上报已验证
   - GitHub / npm 发布材料已准备
   - npm 目标包名为 `clawsense`，但截至 `2026-05-30` 尚未发布到 npm registry
2. 当前主推进方向是“多模态 OpenClaw 驱动的日常感知与回顾”
   - 重点是事件索引层、轻量媒体库、Daily Review、Skill
3. 官方协议兼容是后续兼容方向
   - 后续会考虑**兼容 OpenClaw 官方控制面**
   - 但不会替换掉当前已经工作的 ClawSense 数据面

这意味着：

- 你现在部署和使用，不需要先等官方 Android Companion 协议兼容完成
- 当前 MVP 仍然使用 ClawSense 自己已经跑通的配对和 ingest 路径
- 后续如果做官方兼容，也会走“官方控制面兼容 + ClawSense 数据面保留”的混合架构

## 1. 当前已经验证通过的能力

下面这些链路已经在真实环境里跑通：

- OpenClaw 服务端地址可被手机访问
- ClawSense 插件可加载
- Android 手机扫码配对成功
- 手机保存永久 `deviceSecret`
- App 重开后跳过重复配对
- 启动前台感知服务
- 服务状态明确显示：
  - `未配对`
  - `启动中`
  - `运行中 · 完整模式`
  - `运行中 · 仅音频`
  - `运行中 · 仅图片`
  - `已停止`
  - `异常`
- 音频 VAD 触发上传
- 基线图片上传默认每 60 秒 1 次
- 当检测到对话活跃窗口时，图片上传临时提升为每 10 秒 1 次，持续 120 秒
- 服务端可收到音频、图片和手动短视频
- 服务端会写入 ClawSense journal
- 服务端会把原始素材落到可读目录
- 浏览器可通过当前 OpenClaw 的同一地址打开轻量媒体库页面
- 服务端可生成 `DailyReview`

## 2. 当前限制

这几个点现在要提前知道：

- 当前仓库更像“可运行的 MVP / 内测版”，还不是完全打磨好的公开发布版。
- 标准安装脚本 `install.sh` 在常规 Linux 环境可用，但在 **2GB 内存服务器** 上，安装 OpenClaw 时可能因为 `npm install` 被系统 OOM 杀掉。
- 如果服务端没有可用的多模态主模型，ClawSense 仍可工作，但回顾质量会明显下降。
- 如果服务端没有可用的 STT / Embedding / Vision 后端，ClawSense 仍然可以上传成功，但摘要可能降级成：
  - 音频：`rms=...`
  - 图片：回退描述
- 当前还没有完整的“设备管理后台页面”，设备查看主要通过 CLI。
- 当前媒体库是轻量原始感知浏览页，不是完整的固定 Web 回顾产品。
- Android 端已支持手动 6 秒视频片段采集 / CameraX 录制 M2；Phase 9 新增默认关闭的“自动视频 evidence 增强”，用户显式开启后才会按关键语音 / 文字 / OCR 线索低频录制 6 秒短片段。
- 视频首版走 `hostModelVideoMode=keyframes`：上传 video-only MP4，同时附带起止关键帧，服务端把关键帧证据回链到原视频片段。
- 自动视频不是全天录像：它受服务端队列状态、冷却时间、小时 / 每日上限和前台服务状态保护；连续录像、端侧预缓存和长视频切片仍不在当前 MVP 范围内。
- 当前不会自动给出微表情、情绪或内在意图结论。

## 3. 推荐环境

### 服务端推荐配置

- Linux 服务器或本地 Linux / macOS 电脑
- 推荐内存：`4GB` 及以上
- 推荐模型：OpenClaw 当前主模型使用原生多模态模型
- 如果只有 `2GB`：
  - 可能需要额外配置 `swap`
  - 仍可能在安装 OpenClaw 时失败
- 至少需要手机能访问到服务端当前地址
- 需要放行 OpenClaw 端口
  - 本次验证使用的是 `18789`

### Android 客户端推荐配置

- Android 10 及以上
- 有摄像头和麦克风
- 能正常授予：
  - 相机权限
  - 麦克风权限
  - 通知权限

### 本次已验证环境

- OpenClaw：`2026.3.2`
- Android：Android 13
- 真机：OPPO `PDEM10`

## 3.1 多 Provider / 多模型该怎么配

如果你准备把这个项目开源给不同用户，最重要的一点不是“模型名能不能改”，而是：

- **ClawSense 最稳的跨部署配置方式，应该显式写 OpenAI-compatible endpoint**

原因很现实：

- 不同 OpenClaw 部署暴露 provider 元信息的 schema 并不完全一致
- 有的部署只有主模型名，没有可被 ClawSense 稳定消费的 provider map
- 所以当前最稳的做法不是赌 runtime provider auto-discovery，而是直接给 ClawSense 写：
  - `openaiApiKey`
  - `openaiBaseUrl`
  - `visionProvider`
  - `visionModel`

这里的：

- `visionProvider = openai`

并不是说你必须使用 OpenAI 官方模型，而是：

- **ClawSense 走 OpenAI-compatible SDK 路径**

如果你的 provider 暴露 OpenAI-compatible endpoint，一样可以这样配。

### 当前最推荐的通用规则

建议记住这 4 条：

1. 优先使用纯模型名，不要把 `provider/model` 拼在一起
2. provider 和 model 尽量分开表达
3. 如果 provider 支持 OpenAI-compatible API，直接把 endpoint 写进 ClawSense 插件配置
4. 不要假设所有 OpenClaw 部署都有同一套 `providers` / `models.providers` schema

更推荐：

```text
model = qwen3-max-2026-01-23
provider = alibaba-cloud
```

不够通用：

```text
model = alibaba-cloud/qwen3-max-2026-01-23
```

### 方案 A：OpenAI 官方

如果你就想走最直接、最少解释成本的一条路：

```bash
openclaw config set plugins.entries.clawsense.config.openaiApiKey "\"$OPENAI_API_KEY\"" --strict-json
openclaw config set plugins.entries.clawsense.config.openaiBaseUrl "\"https://api.openai.com/v1\"" --strict-json
openclaw config set plugins.entries.clawsense.config.visionProvider "\"openai\"" --strict-json
openclaw config set plugins.entries.clawsense.config.visionModel "\"gpt-4.1-mini\"" --strict-json
openclaw config set plugins.entries.clawsense.config.sttFallbackModel "\"whisper-1\"" --strict-json
openclaw gateway restart --json || openclaw gateway start --json
```

适合：

- 你本来就在用 OpenAI
- 你希望图片 fallback 和 STT fallback 都在同一 vendor 上

### 方案 B：DashScope / Qwen（北京）

如果你在用阿里云 Model Studio 的 OpenAI-compatible 接口：

```bash
openclaw config set plugins.entries.clawsense.config.openaiApiKey "\"$DASHSCOPE_API_KEY\"" --strict-json
openclaw config set plugins.entries.clawsense.config.openaiBaseUrl "\"https://dashscope.aliyuncs.com/compatible-mode/v1\"" --strict-json
openclaw config set plugins.entries.clawsense.config.visionProvider "\"openai\"" --strict-json
openclaw config set plugins.entries.clawsense.config.visionModel "\"qwen3-omni-flash\"" --strict-json
openclaw config set plugins.entries.clawsense.config.sttFallbackModel "\"qwen3-asr-flash\"" --strict-json
openclaw gateway restart --json || openclaw gateway start --json
```

建议 runtime primary 也尽量写成纯模型名，例如：

```text
agents.defaults.model.primary = qwen3-max-2026-01-23
```

补充说明：

- 北京区 endpoint 是 `https://dashscope.aliyuncs.com/compatible-mode/v1`
- 如果你用的是别的地区，请换成你的 key 对应的地区 endpoint
- `qwen3-omni-flash` 之所以适合当前 ClawSense fallback，是因为它在 OpenAI-compatible 路径下更容易同时覆盖图片和音频理解
- 实时语音提问转写建议用 `qwen3-asr-flash`；`whisper-1` 是 OpenAI 模型名，用 DashScope key 时通常不应该填它

### 方案 C：任意其他 OpenAI-compatible Provider

如果你不是 OpenAI，也不是 DashScope，但你的服务支持 OpenAI SDK 格式：

```bash
export CLAWSENSE_COMPAT_KEY="replace-me"
export CLAWSENSE_COMPAT_BASE_URL="https://your-provider.example/v1"
export CLAWSENSE_COMPAT_VISION_MODEL="replace-with-a-real-vision-or-omni-model"

openclaw config set plugins.entries.clawsense.config.openaiApiKey "\"$CLAWSENSE_COMPAT_KEY\"" --strict-json
openclaw config set plugins.entries.clawsense.config.openaiBaseUrl "\"$CLAWSENSE_COMPAT_BASE_URL\"" --strict-json
openclaw config set plugins.entries.clawsense.config.visionProvider "\"openai\"" --strict-json
openclaw config set plugins.entries.clawsense.config.visionModel "\"$CLAWSENSE_COMPAT_VISION_MODEL\"" --strict-json
openclaw gateway restart --json || openclaw gateway start --json
```

适合：

- 你不想依赖 OpenClaw runtime provider 自动发现
- 你希望 ClawSense 在不同部署里都按同一逻辑解析 client

### 配完以后怎么确认是不是生效

不要只看“服务能启动”，要做一个最小验证：

1. 说一段清晰的 `5-10s` 中文
2. 等一张新的图片上传
3. 再看：

```bash
openclaw clawsense context last-hour
```

或者直接检查：

```text
~/.openclaw/plugins/clawsense/state.json
```

重点关注：

- `analysisProvider`
- `analysisStatus`
- `analysisFailureReason`

你真正想看到的是：

- image 不再是 `visual summary unavailable`
- audio 不再是 `speech transcription unavailable`
- 新事件里 `analysisStatus = succeeded` 的比例明显提高

## 4.1 部署完成后你会多出什么

部署完成后，除了原有的配对与上传接口，你还可以直接使用这些命令：

```bash
openclaw clawsense pair
openclaw clawsense devices
openclaw clawsense status
openclaw clawsense doctor
openclaw clawsense video-config
openclaw clawsense media today
openclaw clawsense review today
openclaw clawsense followups today --focus what_happened
```

浏览器里还能打开轻量媒体库：

```text
http://你当前访问 OpenClaw 的同一地址/plugins/clawsense/library

页面会继续复用你当前访问 OpenClaw 的同一地址，但首次打开媒体库时，需要输入当前 OpenClaw 的 gateway token。这个 token 只保存在当前浏览器。
```

原始素材的保留策略有两层：

- 默认时间上限：`7 天`
- 默认原始素材软上限：`2 GiB`

这表示：

- 正常情况下，原始音频、图片和视频尽量保留到 7 天
- 但如果主机上的 ClawSense 原始素材总量超过 `2 GiB`，系统会优先删除**最早的音频、图片和视频原件**
- 事件索引和 Daily Review 不会因为原件删除而一起消失

所以 `7 天` 更准确地说是“保留上限”，不是绝对保证。对轻量云主机来说，这是为了避免原始素材把磁盘吃满。

建议把日常使用路径理解成 3 个入口：

1. `openclaw clawsense devices`
   用来确认哪台旧 Android 手机已经配对、是否还在线。
2. `openclaw clawsense media today` 或 `/plugins/clawsense/library`
   用来看原始感知库，按日期、设备、音频 / 图片 / 视频快速确认今天到底采到了什么。默认应复用你当前访问 OpenClaw 的同一地址，而不是跳转到任何 ClawSense 官方域名。
3. `openclaw clawsense review today` 或 ClawSense Daily Review Skill
   用来生成助理式回顾，重点看人物、项目、关键细节和后续追问。
4. `openclaw clawsense followups today --focus what_happened`
   用来拿到结构化“一键继续追问”建议（音频 / 视频 / 历史记忆），方便直接喂给聊天页按钮或手动复制追问。

这里要特别记住：

- 媒体库是“原始感知浏览面”，不是最终回顾页
- 媒体库的默认产品目标是：同 host、同 origin、零额外配置
- 不要求你自己配置域名或反向代理
- 不依赖 ClawSense 自己的公网中转域名
- 真正的助理式总结，应该走 `review` 命令或 Daily Review Skill

## 4.2 Daily Review 具体怎么用

目前 Daily Review 已经可以直接使用，最直接的方式是：

```bash
openclaw clawsense review today
openclaw clawsense review 2026-03-10
```

推荐顺序是：

1. 先打开 `/plugins/clawsense/library`
   - 确认今天是否真的采到了足够的音频、图片和必要的视频/keyframe
   - 看看有没有缺采、断采、或“原件已清理”的情况
2. 再运行 `review`
   - 让 OpenClaw 按当天事件窗口生成助理式回顾

Daily Review 会尽量输出固定结构：

- `Today at a glance`
- `时间线回顾`
- `关键人物`
- `关键项目 / 主题`
- `值得注意的细节`
- `今天遗漏但值得追问的点`
- `明天建议关注的事情`

它现在的工作方式是：

1. 读取当天已经索引好的 `CaptureEvent`
2. 按会话窗口整理音频、图片和视频/keyframe
3. 优先使用当前 OpenClaw 的多模态主模型分析关键窗口
4. 多模态不可用时，再退回结构化 fallback

需要知道的现实情况是：

- `review` 现在已经能跑，也适合每天试用
- 但它最终能不能像真正的私人助理一样讲清楚一天，仍然取决于：
  - 音频转写质量
  - 图片视觉摘要质量
  - 人物注释是否完整
  - 当前 OpenClaw 主模型本身的能力

如果你看到很多：

- `rms=...`
- `Image captured but visual summary was unavailable.`

说明采集和索引链路是通的，但当前素材理解质量还不够高，Daily Review 会更像“结构化回顾草稿”，而不是最终成熟体验。

## 4.2.1 普通聊天页怎么正式进入 ClawSense

如果你不是在终端里跑 `openclaw clawsense review today`，而是在普通聊天页里想问：

- “总结过去一个小时我需要注意的地方”
- “回顾今天发生了什么”
- “把今天最值得记住的 3 件事告诉我”

正确进入方式也不是“让模型自己去扫文件系统”，而是显式走 ClawSense 的 skill / tool。

建议顺序是：

1. 先读 `review`
2. 不够时再读 `events`
3. 还不够时才读受控 `artifacts`

也就是说：

- 普通聊天页和 CLI 走的是同一套 ClawSense 数据面
- 不是绕过事件索引直接去读任意文件
- 如果真的要看原件，也必须只限于 ClawSense 管理的媒体目录

## 4.3 人物 / 项目标注现在怎么补

当前最小可行的补充路径是：

1. 先打开 `/plugins/clawsense/library`
   - 确认这一天到底有没有采到足够素材
2. 再跑 `openclaw clawsense review today`
   - 看看哪些人物、项目、细节仍然不清楚
3. 对 review 里最关键的追问先做回答
   - 例如“这个人是谁？”
   - 例如“这段属于哪个项目或生活主题？”

如果你已经知道某个人的身份，当前可以直接写回人物注释：

```bash
openclaw clawsense annotate <personRef> <displayName> [notes...]
```

或者走现有 HTTP 入口：

```text
POST /api/clawsense/annotations
```

人物注释最值得补的字段是：

- `displayName`
- `relationship`
- `notes`
- `nextWatchFor`

当前要明确一个边界：

- 人物注释已经有现成入口
- 项目 / 主题补充当前主要还是走 review 追问，不单独开一套新命令和新协议
- 这轮目标是先把“媒体库 -> review -> 补标注”这条路径走顺，而不是把产品扩成重型后台

## 4. 服务端部署

### 路线 A：标准环境（推荐）

适合：

- `4GB` 及以上内存的服务器
- 或本地电脑开发环境

步骤：

1. 安装 OpenClaw 稳定版  
   参考 OpenClaw 官方安装方式。

2. 让服务器拿到 ClawSense 插件来源  
   这里有 3 种方式，当前项目更常用的是前两种：

   方式 A：直接把整个仓库传到服务器
   - 适合当前这种“源码还在你自己手里、还没正式发布”的阶段
   - 常见做法：
     - 在服务器上 `git clone 你的仓库地址`
     - 或在本地把仓库打包后，用 `scp` 上传到服务器再解压
   - 这种方式下，服务器上最终会有这些文件：
     - `install.sh`
     - `index.ts`
     - `src/*`

   方式 B：给 `install.sh` 一个远程压缩包地址
   - 适合你把插件源码打成 `tar.gz`，放到对象存储、GitHub Release、静态文件服务器之后使用
   - 然后在服务器上执行：

```bash
CLAWSENSE_SOURCE_URL="https://your-host.example/clawsense-plugin.tar.gz" bash install.sh
```

   - `install.sh` 会自己先下载这个压缩包，再安装插件

   方式 C：插件发布到 npm 后
   - 适合后续正式发布阶段；当前 `clawsense` 包名尚未发布到 npm registry
   - 然后在服务器上执行：

```bash
CLAWSENSE_NPM_SPEC="clawsense@latest" bash install.sh
```

   - `install.sh` 会直接走 `openclaw plugins install <npm-spec>`

   当前这份仓库还没有默认公开下载地址，所以文档里说“获取本仓库源码”，本质上就是：
   - 你先把源码仓库放到服务器
   - 或者给服务器一个可下载的插件压缩包 URL
   - 并不是服务器会自动知道该去哪里下载

   当前维护者视角下更稳的现实建议是：
   - **npm 发布前：优先使用已经打包好的 `.tgz` 插件包或源码安装**
   - **npm 发布后：优先使用 `CLAWSENSE_NPM_SPEC="clawsense@latest"` 安装**
   - 直接在源码目录执行 `bash install.sh` 适合开发和维护场景，但不是当前最稳的对外通用安装方式
   - 如果你走源码路径，请先确认插件入口所需的打包产物已经齐全

3. 如果你走的是“方式 A：直接把仓库放到服务器”，就在仓库根目录执行：

```bash
bash install.sh
```

这个脚本会做几件事：

- 检测 OpenClaw 是否存在
- 必要时安装 OpenClaw `2026.3.2`
- 安装 ClawSense 插件
- 启用插件并加入 `plugins.allow`
- 重启 OpenClaw Gateway
- 直接在终端里执行 `openclaw clawsense pair`

安装完成后，推荐你优先确认两件事：

1. `openclaw clawsense media today` 能正常返回 JSON
2. 浏览器能通过你当前访问 OpenClaw 的同一地址打开 `/plugins/clawsense/library`

如果你要验证 Android 手动 6 秒视频片段，还需要先打开视频 ingest：

```bash
openclaw config set plugins.entries.clawsense.config.hostModelVideoMode "\"keyframes\"" --strict-json
openclaw gateway restart --json || openclaw gateway start --json
openclaw clawsense video-config
```

`keyframes` 是当前推荐模式：手机上传 video-only MP4，同时附带起止关键帧，服务端先把关键帧作为可理解证据挂回原视频片段。

### 路线 B：低内存服务器（2GB 机器）

适合：

- 阿里云轻量 / 低配 VPS
- 标准 `npm install` 会被 OOM 杀掉的环境

需要知道：

- 当前 `install.sh` 不保证在 2GB 机器上一次成功
- 这类环境更稳的做法是：
  - 先把 OpenClaw 运行时做成预打包运行目录
  - 再把 ClawSense 插件做成预装依赖包
  - 上传到服务器后手工解压部署

也就是说：

- **标准用户路径**：优先用 `install.sh`
- **低内存例外路径**：当前仍属于维护者支持的部署方式，不算最终对外一键发布形态

## 5. OpenClaw 地址与访问方式

手机要能访问到服务端，所以需要确认：

- Gateway 已启动
- 端口已放行
- 浏览器和手机都能访问当前 OpenClaw 的地址

例如：

```bash
curl -i http://你的OpenClaw地址:18789/
```

如果返回 OpenClaw Control 的 HTML 页面，说明公网访问基本正常。

这里要特别说明：

- ClawSense 不应该要求你通过“ClawSense 官方公网域名”访问自己的媒体库
- 默认访问方式应该直接复用你当前已经能打开 OpenClaw 的地址
- 对大多数只有一台轻量云主机、只知道一个 OpenClaw 地址的用户来说，这必须是零额外配置的

## 6. 生成配对二维码

在服务端执行：

```bash
openclaw clawsense pair
```

它会在终端输出：

- 一个大号 ASCII 二维码
- 一段 JSON

JSON 里通常会包含：

- `token`
- `expiresAt`
- `ttlSeconds`

注意：

- `setup token` 只用于首次配对
- 不需要每次启动都重新扫码

## 8. 启动感知服务后，页面状态是什么意思

这是当前 App 最重要的状态说明。

### `未配对`

表示：

- 手机还没有换到永久 `deviceSecret`
- 现在不能真正开始上传

### `启动中`

表示：

- 你刚点击了 `启动感知服务`
- App 已经开始切换到前台服务
- 一般会在 1 到 2 秒内进入运行状态

如果长时间停留在这里，通常要检查：

- 通知权限
- 前台服务是否真的起来
- 当前 App 是否是最新构建

### `运行中 · 完整模式`

表示：

- 音频 VAD 正在运行
- 定格拍照正在运行
- 心跳正在运行

这是最完整的正常状态。

### `运行中 · 仅音频`

表示：

- 麦克风在工作
- 相机没有参与
- 心跳仍然正常

常见原因：

- 相机权限没给
- 某些机型上相机前台服务受限制

### `运行中 · 仅图片`

表示：

- 相机在工作
- 麦克风没有参与
- 心跳仍然正常

常见原因：

- 麦克风权限没给

### `已停止`

表示：

- 前台服务已停止
- 音频采集停止
- 定格拍照停止
- 心跳停止

### `异常`

表示：

- 服务启动过，但某个关键步骤失败了

比如：

- 没有找到已配对设备
- 相机初始化失败

## 9. 真机验证时应该怎么判断“真的在工作”

### 音频

启动服务后：

- 对着手机说话 3 到 5 秒
- 服务端应该出现新的 `audio` 记录

当前 journal 文件通常在：

```bash
~/.openclaw/plugins/clawsense/state.json
```

### 图片

启动服务后：

- 基线模式大约每 `60` 秒拍 1 次
- 如果刚发生过音频活跃窗口，图片会临时提升为每 `10` 秒 1 次
- 活跃窗口默认持续 `120` 秒

如果手机日志里出现：

- `Still capture saved`
- `Uploading image`
- `Image upload succeeded`

就说明图片链路已经通了。

## 11. 常见问题

### 11.1 点了启动服务，但不知道是否真的成功

看 App 里的“服务状态”卡，不要只看按钮。

正确判断方式：

- `启动中`：正在切换前台服务
- `运行中 · 完整模式`：已经成功
- `已停止`：已经停掉

### 11.2 扫码成功，但配对失败

优先检查：

- 服务端二维码是否刚生成，`token` 是否还在 10 分钟有效期内
- Host 是否写对
- 手机是否能访问当前 OpenClaw 地址

### 11.3 服务端安装 OpenClaw 时被系统杀掉

典型表现：

- `npm install` 出现 `Killed`
- `journalctl -k` 里能看到 OOM

优先建议：

- 换 `4GB` 及以上内存机器
- 或临时增加 `swap`
- `2GB` 机器当前不算稳定推荐配置

### 11.4 音频上传成功了，但摘要只有 `rms=...`

这说明：

- 录音和上传链路没问题
- 但服务端当前没有真正可用的语音转写后端

也就是说：

- **主链路已通**
- **智能摘要能力还没完全接上**

### 11.5 图片总是不上来

优先检查：

- 手机是否给了相机权限
- 服务是否处于运行中
- 日志里是否有：
  - `Still capture saved`
  - `Uploading image`
  - `Image upload succeeded`

## 12. 当前更适合怎么使用这个项目

当前最适合的定位是：

- 一个已经能跑通主链路、并开始强调“多模态日回顾”的 ClawSense MVP
- 适合内测、验证日常采集流程、继续迭代媒体库和 DailyReview

最适合先继续做的事情是：

2. 接更稳定的 STT 兜底能力
3. 做设备管理页和失败重试队列
