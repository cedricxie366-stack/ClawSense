# ClawSense 架构师交接摘要

这份文档用于把当前项目状态、长期职责和下一步优先级，交接给新的“架构师 / 统筹 agent”。

## 1. 项目一句话

ClawSense 是一个 **OpenClaw 插件 + Android 客户端** 项目，用旧 Android 手机做可穿戴感知节点，持续采集音频、图片和心跳，并在 OpenClaw 上形成：

- 可浏览的原始感知库
- 可生成的 `context`
- 可生成的 `Daily Review`

## 2. 当前阶段

项目当前已经跨过了“能不能跑”的阶段，也已经跨过了“语义主链还没成立”的阶段，进入：

- `Phase 1` MVP 真实可用
- `Round-4 P0` 已真实收口
- 当前主推进方向切换到：
  - 普通聊天页正式接入 ClawSense
  - 人物 / 项目最小标注闭环
  - 开源部署标准化
  - 更自然的助理表达

不是从零开始，也不是还在纯链路打通阶段；而是一个已经打通主链路、并已经让图片/音频语义链在真实环境中成立的项目。

## 4. 当前真正的问题，不是“功能不存在”

当前最主要问题已经不再是：

- 图片大量 unavailable
- 音频大量 unavailable
- 长对话完全无法表达成连续窗口

这些核心阻塞在 Round-4 里已经被打掉。

当前新的主问题是：

- **开源部署标准化仍不足**
- **普通聊天页还没完成正式接线**
- **助理表达虽然成立，但还不够最终 polished**

所以项目现在的正确判断是：

- **功能可用**
- **链路已通**
- **媒体库可看**
- **review / context 可跑**
- **语义主链已成立**
- **但“开箱即用的多 provider 标准化”还没完全收口**

## 5. 产品方向共识

当前全项目统一口径：

- **推荐运行在由原生多模态大模型驱动的 OpenClaw 上**
- 多模态模型是主分析引擎
- `runtime STT` 只做兜底
- 当前数据面仍然是 ClawSense 自己的 ingest 路径
- 后续可以考虑“官方控制面兼容 + ClawSense 数据面保留”的混合架构
- 但现在不会把当前已跑通的数据面整体替换成官方 Android Companion / node 协议

明确边界：

- 允许手动 6 秒短视频 evidence。
- 允许默认关闭、用户显式开启、受队列背压 / 冷却 / 上限保护的主动短视频 evidence 增强。
- 不做全天连续录像、端侧环形 pre-buffer、长视频自动切片。
- 不做不可解释、不可关闭的语音开启视频。
- 不做微表情自动结论。
- 不做重型固定 Web 回顾页。

## 6. 媒体库的产品约束

当前已经确认的产品约束：

- 媒体库不应依赖 ClawSense 官方公网域名
- 不要求用户自己配置域名 / 反向代理 / 额外路由
- 默认复用用户当前访问 OpenClaw 的同一地址
- 目标是：
  - 同 host
  - 同 origin
  - 独立轻量页
  - 不耦合 Control UI 聊天页

当前入口：

- `http://<openclaw-host>/plugins/clawsense/library`

页面内用 **gateway token** 请求素材索引和原件，token 只存在浏览器本地。

## 7. 当前最值得额外记住的配置结论

这是本轮真实验收里最重要的新知识点。

### 7.1 当前最稳的跨部署方式

对开源用户来说，目前最稳的现实方式不是依赖 OpenClaw runtime 自动发现 provider，而是：

- 直接给 ClawSense 插件写显式 OpenAI-compatible 配置：
  - `openaiApiKey`
  - `openaiBaseUrl`
  - `visionProvider`
  - `visionModel`

### 7.2 `visionProvider = openai` 的真实含义

这里的：

- `visionProvider = openai`

不是“只能用 OpenAI 官方”，而是：

- **使用 OpenAI SDK / OpenAI-compatible 路由**

只要你的 provider 暴露 OpenAI-compatible endpoint，就可以这么配。

### 7.3 当前不够标准的地方

当前最大的不稳定因素不是模型名，而是：

- provider 元信息在不同 OpenClaw 部署中的表达方式并不统一

所以现在的准确评价是：

- ClawSense 已支持多模型
- 但还没有完全做到“不同 provider schema 天然零适配开箱即用”

## 8. Daily Review 当前状态

命令可用：

```bash
openclaw clawsense review today
openclaw clawsense review YYYY-MM-DD
```

当前 review 结构目标固定为 7 段：

1. `Today at a glance`
2. `时间线回顾`
3. `关键人物`
4. `关键项目 / 主题`
5. `值得注意的细节`
6. `今天遗漏但值得追问的点`
7. `明天建议关注的事情`

当前问题不是“有没有 review”，而是：

- review 虽然已有真实语义输入，但还没有完全达到最终助理感

## 9. retention / 原件保留现状

当前逻辑：

- 原始音频 / 图片默认最多保留 `7 天`
- 同时默认受一个 `2 GiB` 的原件软上限控制
- 超过上限时，最早原件先删
- 事件索引和 Daily Review 保留

已经修复的历史问题：

- 旧 `journal -> artifacts/events` 迁移时，原件曾被错误地立即判过期
- 新版本已修复
- 已物理删除的旧原件不会自动恢复

## 10. 当前多 agent 结构

当前建议结构不是“一个超级 agent 全做”，而是：

- `1` 个统筹 / 架构 agent
- `3` 个执行 agent

### Android / Sensor Agent

负责：

- Android 前台服务
- 音频 VAD
- CameraX
- 上传稳定性
- 权限与状态反馈

### Backend / Event Intelligence Agent

负责：

- `RawArtifact`
- `CaptureEvent`
- `PersonAnnotation`
- `DailyReview`
- 事件窗口
- STT fallback
- retention
- review engine
- provider 兼容与 failure 分类

### Review / Product Agent

负责：

- 轻量媒体库体验
- Daily Review 的表达质量
- Skill
- README / Guide / Demo 路线
- 开源部署说明的可复制性

## 12. 当前最值得推进的开发优先级

### P1：完成产品闭环

最重要：

- 普通聊天页正式接入 ClawSense skill / tool / context
- 人物 / 项目标注最小闭环
- 用“值得留意的社交线索”替代心理学式结论

### P2：补开源部署标准化

重点：

- 固化多 provider 配置模板
- 统一 README / 部署文档 / release 文档的配置口径
- 尽量减少用户对 runtime provider schema 的依赖

### P3：进一步提升 Daily Review 助理感

重点：

- 关键人物不要空
- 关键项目不要掉回技术标签
- 值得注意的细节要能解释“为什么值得记住”
- 追问要像真正助理会问的问题

### P4：后续兼容 OpenClaw 官方控制面

这件事是后续方向，不是当前主线。

## 13. 当前不建议优先做的事

新的架构师 agent 应明确压住这些冲动：

- 不要回头重写成官方 Android Companion 协议
- 不要现在做视频产品线
- 不要直接上重型 Web app
- 不要因为“已经支持多模型”就误判为标准化已经完成
- 不要把当前已经跑通的主链路推翻重做

## 14. 对新架构师 agent 的一句话要求

如果只用一句话定义新架构师 agent 的职责：

**守住共享契约，守住多模态优先路线，补齐开源部署标准化与产品闭环，在不推翻主链路的前提下，把 ClawSense 推到更可复制、可演示、可公开传播的产品状态。**
