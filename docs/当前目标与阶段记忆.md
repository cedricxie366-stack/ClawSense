这份文档用于防止项目在连续迭代中出现目标漂移、阶段混淆和“只顾修局部、不顾最终效果”的情况。

## 1. 长期目标

ClawSense 的长期目标不是做一个“先替 OpenClaw 总结完”的插件，而是做一个：

- 全天候、多模态的证据采集与记忆层
- 为 OpenClaw 主模型持续提供可检索、可回放、可复核的 evidence
- 让 OpenClaw 在晚上能够像一个真正理解过全天素材的助理那样回答：
  - 今天发生了什么
  - 有什么需要注意
  - 哪些细节你可能没注意到

最终目标体验更接近：

- 用户挂着旧手机一天
- ClawSense 尽可能保住当天所有语音、图片、视频细节
- OpenClaw 主模型基于这些 evidence 做最终理解
- 甚至主动指出用户当时没有留意到的人、任务、知识点和异常点

## 2. 早期传播场景优先级

早期最重要的传播场景不是聚会，而是：

1. 办公
2. 上学 / 课堂
3. 聚会 / 社交（作为 showcase 示例）

这意味着当前产品最应优先证明的价值是：

- 办公：
  - 今天别人给我布置了什么任务
  - 哪些人物值得注意
  - 会议里别人是怎么说的
  - 明天要继续跟进什么
- 上学：
  - 今天老师讲了哪些重点
  - 有哪些学习要点 / 作业 / deadline
  - 哪些地方当时没注意，晚上要补看

### 2.1 当前 PMF 收窄（2026-04-23）

当前阶段的产品判断进一步收窄为：

- **优先服务“云端 OpenClaw + 旧手机 + 办公打工人”场景**
- 典型用户不是先在本机自建局域网链路，而是已经在使用：
  - 阿里 / 腾讯 / 字节 / 智谱等云端龙虾产品
  - 再配一个旧手机做全天感知入口
- 因此当前阶段的“可发布”标准，应优先围绕：
  - 云端 OpenClaw 可稳定接入 ClawSense
  - 旧手机可稳定上传音频 / 图片 / 视频
  - 晚上问 OpenClaw 时，能围绕办公场景给出有用回顾

这意味着：

- **本机环境 / 异地直连 / 局域网穿透不是当前主阻塞**
- 本机场景仍然重要，但放到下一阶段再系统收口
- 当前不因为本机场景尚未标准化，就阻塞云端办公场景的推进和发布

## 3. 当前主线调整（2026-05-12）

当前主线从“音频 + 图片总结器”调整为：

> **ClawSense 是 OpenClaw 的现实世界语音入口。**

这意味着当前最重要的产品闭环不是先把视频、OCR、speaker diarization 全部做完，而是先证明：

- 用户可以通过旧手机直接和 OpenClaw 大模型语音沟通
- ClawSense 负责把现实世界 evidence 检索出来
- OpenClaw 主模型负责理解、推理、追问、建议和沉淀
- 手机负责把主模型回答用 TTS 读出来，并显示完整文本

用户不只是问“总结一下”，还会继续追问：

- `过去4小时我们聊了什么？`
- `昨天发生了什么？`
- `你怎么看这件事？`
- `这里面有什么我没注意到的？`
- `帮我整理成会议纪要。`
- `把刚才讨论的行动项沉淀成文档。`
- `这件事跟我们之前聊的项目有什么关系？`

因此当前阶段的优先级调整为：

1. **语音对话入口稳定**
   - 显式提问、ASR、服务端问题理解、TTS 播报、屏幕完整答案稳定。
2. **时间范围和证据路由稳定**
   - `刚才 / 过去4小时 / 今天 / 昨天` 能选对 evidence 范围。
3. **接入大模型回答**
   - 本地模板只做兜底；可用时应由 OpenClaw/主模型基于 evidence 生成自然回答。
4. **连续追问与可执行意图**
   - 支持“详细说说 / 你怎么看 / 帮我整理成文件”这类对话式意图。
5. **再增强识别能力**
   - ASR、speaker、OCR、视频是 evidence 质量增强，不再抢占当前主线。

### 3.1 数据面可靠性与主动视频的融合判断（2026-06-02）

`ingest` 队列拥堵和“语音 / 文字主动触发录视频”不是两条支线，而是当前主线的同一个基础问题：

- 实时语音助手要可用，前提是音频、图片、视频证据能先稳定落库，不能被 ASR / 多模态分析超时卡死。
- 全天回顾要可信，前提是原始 artifact 和 pending event 先保住，后续可以异步补 transcript、caption、OCR、speaker。
- 自动录视频要有价值，前提是它只是“关键时刻证据增强”，不能在服务端拥堵时继续制造大文件洪水。

因此下一阶段的融合原则固定为：

1. **先修数据面可靠性**
- 上传请求只负责保存 artifact 与创建 pending evidence，分析进入后台队列。
- `ingestQueue` 和 `analysisQueue` 拆开，避免单条音频超时拖住全部图片 / 视频。
- 2026-06-02 最小闭环已落地：上传先返回 `202`，后台 `analysisQueue` 异步回填；`analysis_pending` 会被周期性补排；新增 queue-status / analysis-retry；Android 已能展示最近一次上传的后台分析队列状态。
- 2026-06-02 端侧节流验证面已补齐：Android live report 会统计 still/audio/auto-video 节流信号；Debug APK 可用 `scripts/check-android-live.sh inject-throttle` 注入临时队列高水位，用于验证端侧逻辑，但不替代真实拥堵压测。

2. **再做主动视频触发**
- 从 transcript、OCR/caption、显式语音命令、近期问题中识别“这里值得录一段”的信号。
- 触发前必须检查队列状态、冷却时间、每日上限和隐私状态。
- 录制结果必须带上 `triggerReason` / `sourceEventId` / `sourceText`，让 OpenClaw 后续能解释“为什么录了这段”。
- 2026-06-02 最小闭环已落地：Host 在分析完成后生成一次性 `video_clip` directive，Android 通过前台服务 heartbeat 接收，并在用户显式开启自动视频、队列不拥堵、冷却和上限允许时自动录制 6 秒视频，note 写入触发原因与来源 evidence。

3. **最终仍回到 evidence-first 对话**
- 主动视频不是为了让插件替模型总结，而是为了给 OpenClaw 主模型补一段可回放、可复核的视觉 evidence。

## 4. 短期目标

当前短期目标不是“一次性吃下整天所有原始媒体”，而是先把下面这条链做稳：

1. 证据层稳定采集
- 音频、图片、视频 / 关键帧可持续进入系统

2. 证据层可持续补强
- degraded 音频能够通过 query-time recheck / ASR backfill 逐步补成 transcript

3. 语音对话入口能基于 evidence-first 方式给出有用回答
- 不是只会说“今天拍到了什么”
- 而是开始说：
  - 任务候选
  - 人物候选
  - 学习要点
  - 环境线索
  - 待确认重点
  - 对事情的理解、建议和可沉淀输出

4. 用户能开始标注说话人 / 人物
- 例如：
  - `speaker_1 = 李三`
  - `speaker_2 = Amy`

## 6. 当前仍未完成的核心问题

下面这些问题仍然是阶段主矛盾：

1. 整天语音细节的覆盖率还不够高
- ASR 能跑通
- 但重度音频日仍然不能快速补齐整天 transcript

2. speaker layer 还没有真正 diarization
- 现在已有：
  - `speaker_1 / speaker_2` 占位
  - speaker annotation 回填
- 还缺：
  - 更稳定的说话人切分与复用

3. 聊天页虽然已能回答，但离“指出你没注意到的点”还有距离
- 目前更像：
  - 证据整理器 + 初步助理回答
- 还不够像：
  - 全天记忆基础上的主动洞察

4. 设备接入与端侧稳定性仍是体验瓶颈
- `bind=lan` / `127.0.0.1` / 心跳 token 漂移 / Android 输入可读性问题，会直接影响真实采集覆盖率
- 这类“接入摩擦”会让我们在问答层看起来像模型能力不足，实际是数据没稳定进来
- 当前最终硬缺口更具体：物理 Android 自动证据已生成，no-arm ambient 已通过，但 primary live 仍缺真人确认 `HUMAN_TTS_OK=1` 与 `HUMAN_ANSWER_RELEVANT=1`；没有这两个确认时，`npm run check:stage-final` 必须失败，不能把自动日志当作人工体验验收

5. （已收口）跨 provider fallback 的 P1 技术债
- 已修复：fallback 触发条件已包含 provider 切换，不再只看模型名
- 已补回归：同模型跨 provider 的 image/audio fallback 测试已覆盖

6. 语音 Agent 对话层还在起步
- 现状：
  - 已有显式提问、recent-context、日级回顾、TTS 摘要、连续追问、读全文/停止朗读和草稿文件。
  - 已接入“模型回答 + 模板兜底”的架构。
- 还缺：
  - 更自然地调用 OpenClaw 工具
  - 更稳定地在真实重度音频日里引用 transcript，而不是退回图片描述
  - 更高质量的 answerSpokenText 播报节奏和真人验收

7. 数据面拥堵会放大所有上层问题
- 如果上传请求被慢 ASR / 多模态分析拖住，用户会看到待补传和拥堵，并误以为网络或配对失败。
- 如果 evidence 不能先稳定落库，后续“过去 4 小时 / 昨天 / 刚才重点”都会被迫依赖残缺素材。
- 因此 `fast ingest + async analysis + queue-status` 是进入自动视频和全天高强度采集前的 P0。

8. 主动视频触发还缺安全阈值
- 当前已有手动短视频闭环，但自动触发必须避免误触、滥录、拥堵时继续加压。
- 首版只允许短片段、低频、事件触发，禁止全天连续录像。
- 后续若要做到“不漏关键瞬间”，需要端侧 pre-buffer / 环形缓存，这是更后面的能力，不作为当前收口门槛。

### 8.1 下一阶段的两条产品线

下一阶段允许并行思考两条产品线，但主次必须明确：

#### A 线：拟人化、实时化的“云端办公助理”

这是**当前第一优先级**，也是最贴近 PMF 的方向。

目标不是再做一个“晚上回顾工具”，也不只是“白天可追问”，而是让 OpenClaw 在白天就尽可能进入：

- **知道用户此刻正在看什么**
- **知道用户此刻正在听什么**
- **能够围绕这个“当前上下文”与用户做语音互动**

因此这条线的产品中心应理解为：

- `current context companion`
- 而不是单纯的 `meeting recap assistant`

白天用户随时都可以问：

- 你刚才听到了什么？
- 我现在正在看什么？
- 这份屏幕 / 白板 / 文件的重点是什么？
- 刚刚会议里别人怎么说的？
- 我刚才答复了什么？
- 有人来我工位找我吗？
- 现在有什么值得我注意？

这条线的核心建设顺序应是：

1. 当下上下文感知
- 让系统更快知道用户此刻正在看什么、听什么，而不是只在事后生成 recap

2. 低延迟 evidence refresh
- 让聊天问答能消费“刚刚几秒到几分钟”的新音频 / 图片 / 视频证据

3. 会议 / 工位 / 屏幕场景的问答模板化能力
- `刚才说了什么`
- `我现在在看什么`
- `这份内容的重点是什么`
- `今天待跟进的任务`
- `谁来找过我`
- `刚刚讨论的重点`

4. speaker / people layer 做强
- 从 `speaker_1 / speaker_2` 走向更稳定的办公人物识别与用户标注复用

5. desk mode（工位代理模式）
- 用户离开工位时，旧手机持续观察
- 优先回答“来过谁 / 问了什么 / 需要我回什么”
- 是否允许自动代答，要放到更后面并加安全边界

#### B 线：Mac 客户端（数字世界感知终端）

这是**当前第二优先级**，更像下一阶段的新入口，而不是当前 PMF 的主闭环。

这里必须统一一个产品约束：

- **Mac 端不是另一个产品**
- **Mac 端和手机端本质上是 ClawSense 的两种客户端形态**
- 二者应共用：
  - 同一套配对 / 设备模型
  - 同一套上传协议
  - 同一套媒体库
  - 同一套 evidence / retrieval / followups / review 数据面

区别只在于各自更擅长采什么：

- 手机端：
  - 环境音频
  - 拍照 / 定时图片
  - 关键帧 / 轻视频
- Mac 端：
  - 环境或系统音频
  - 屏幕截图 / OCR / active app / window title
  - 后续再考虑录屏

它的价值不是替代旧手机，而是补齐旧手机看不到的那一半：

- 屏幕内容
- IM 聊天上下文
- 文档 / 网页 / 视频 / 新闻浏览轨迹
- 用户在电脑上的任务切换和知识摄入

这条线更适合作为“第二客户端 / 第二感知终端”来做，建设顺序应是：

1. 先复用手机端的客户端思路
- 同样作为“设备”接入
- 同样进入统一媒体库和统一时间线
- 先不搞独立平行的数据系统

2. 增加 Mac 专属的被动屏幕感知
- 定时截图 / OCR / caption / active app / window title
- 先不急着做重型录屏

3. 复用统一的音频链路
- Mac 录音的 ingest 原理和 Android 录音保持一致
- 尽量共用同一套音频 artifact / event / transcript / session 合窗逻辑

4. 再做轻量结构化
- 把屏幕事件纳入同一 evidence bundle / retrieval / followups

5. 再做办公软件专项理解
- 企微 / 飞书 / 微信 / 浏览器 / 文档类页面

6. 最后才考虑录屏与更重的数字证据
- 录屏是后续增强项，不是第一阶段主路径

7. 再把手机端与 Mac 端真正融合成全天多端记忆层

因此当前阶段的结论应固定为：

- **先把 A 线打透，再把 B 线做成第二入口**
- 不要因为 Mac 端很性感，就反过来打断当前云端办公助理主线

## 8. 不应再偏离的原则

以后推进时，应始终遵守下面这些原则：

1. 不要再把 ingest 阶段 summary 当作最终真相
2. 不要把“插件先理解完”当作长期方案
3. OpenClaw 主模型才是最终理解者
4. ClawSense 的定位是 memory / evidence layer
5. 优先服务办公 / 上学场景
6. 所有新功能都要回答一个问题：
- 它是否能让“今天发生了什么 / 有什么需要注意”更接近真实有用？
7. 在下一阶段的所有选择里，默认优先服务云端办公打工人场景
8. Mac 端属于重要增量入口，但不是当前阶段的主完成条件
9. 自动视频必须服从数据面背压，不能为了更强感知牺牲上传稳定性
10. 新增采集能力必须能解释“为什么采集”，并能回链到触发它的语音 / 文字 / 图片 evidence

## 9. 需要持续维护的机制

为防止遗忘，后续应持续维护以下机制：

1. 这份文档
- 目标、阶段、优先级变化时必须更新

2. vNext 任务清单
- 每完成一个阶段性能力，就补充状态或验收口

3. 服务器侧 smoke / backfill 习惯
- 新版本部署后，优先观察：
  - audio backfill 是否在工作
  - 聊天页回答是否更依赖 transcript

4. 真实问答验收
- 不要只看单元测试
- 必须继续用真实问题反复验：
  - 今天发生了什么
  - 有什么需要注意
  - 今天最值得注意的任务和人物是什么
  - 把学习要点和待确认问题分开说

5. 子线程 / 子 agent 分工文档
- 下一阶段继续允许多线程协同，但每个线程都必须有明确职责边界，避免重复探索

## 10. 当前阶段收尾原则

当前阶段不应继续无限扩展“新能力”，而应转入：

1. 冻结目标范围
- 只围绕办公 / 上学场景的晚上回顾做收口
- 不再在本阶段继续扩展新的 showcase 方向
- 聚会 / 社交保持为展示用案例，不作为本阶段完成判定

2. 冻结功能边界
- 本阶段以 evidence-first nightly recap 为终点
- 不再要求在本阶段完成真正的 speaker diarization
- 不再要求在本阶段完成“主动指出你没注意到的所有细节”
- 不再要求在本阶段完成所有 provider 的完美统一

3. 当前阶段完成后再进入下一阶段
- 下一阶段才重点进入：
  - speaker diarization
  - 更高覆盖率的整天级 transcript
  - 主动发现层
  - 更彻底的 provider / ASR / multimodal routing 标准化
