# GitHub 开源方案借鉴（2026-04-23）

这份文档用于回答一个实际问题：

- 我们现在的“云端 OpenClaw + 旧手机 / 后续 Mac 端 + 全天感知助手”路线，GitHub 上有哪些开源项目值得借鉴？
- 哪些适合直接复用？
- 哪些更适合借鉴架构，而不适合直接引入？

## 1. 当前判断

从当前阶段的 PMF 出发：

- 第一优先不是做“本机局域网版”
- 第一优先是做：
  - 云端 OpenClaw
  - 办公打工人
  - 旧手机作为全天感知入口
  - OpenClaw 在白天能围绕“当前看到 / 当前听到”的内容做实时互动

因此这次开源借鉴的重点不是泛泛地找“会议总结工具”，而是找三类能力：

1. 屏幕 / 当前上下文感知
2. 实时语音互动
3. 结构化记忆与可检索 evidence

## 2. 最值得借鉴的项目

### 2.1 screenpipe

- 仓库：
  - [screenpipe/screenpipe](https://github.com/screenpipe/screenpipe)
- 为什么重要：
  - 它几乎就是“Mac / Desktop 第二感知终端”的最强现成参考
  - 核心不是单纯录屏，而是：
    - event-driven screen capture
    - accessibility tree first
    - OCR fallback
    - AI assistant / MCP 可直接查询历史屏幕上下文
- 最值得我们借鉴的点：
  - 不要持续傻录屏，而是**事件驱动采样**
  - 不要凡事都 OCR，优先用**accessibility tree / structured text**
  - 屏幕事件天然就该进可查询 memory，而不是只进视频文件
- 当前结论：
  - **非常适合借鉴到 B 线（Mac 感知终端）**
  - 不适合作为 A 线旧手机路线的直接底座

### 2.2 Omi

- 仓库：
  - [BasedHardware/omi](https://github.com/BasedHardware/omi)
- 为什么重要：
  - 这是当前和我们目标形态最接近的开源项目之一
  - 它直接主打：
    - sees your screen
    - listens to your conversations
    - remembers what you've seen and heard
    - desktop / phone / wearables 多端
- 最值得我们借鉴的点：
  - 产品形态不是“单点工具”，而是**多端感知 + 统一记忆 + AI chat**
  - “记忆、对话、行动项”是同一层，不是分裂的
- 当前结论：
  - **最适合借鉴产品形态和系统边界**
  - 但仓库过大、产品面过宽，不适合现在整仓引入
  - 更适合拆解其：
    - 事件模型
    - memory/chat/action item 的衔接方式

### 2.3 Pipecat

- 仓库：
  - [pipecat-ai/pipecat](https://github.com/pipecat-ai/pipecat)
- 为什么重要：
  - 它专注的是实时语音与多模态 conversational agent
  - 不是“记忆产品”，而是**低延迟语音互动运行时**
- 最值得我们借鉴的点：
  - VAD / turn-taking / voice pipeline orchestration
  - 适合做“你现在在看什么 / 你刚才说什么”的实时交互层
- 当前结论：
  - **适合借鉴到 A 线的实时语音层**
  - 但它本身不解决全天 evidence / memory layer

### 2.4 TEN Framework

- 仓库：
  - [TEN-framework/ten-framework](https://github.com/TEN-framework/ten-framework)
- 为什么重要：
  - 它也是实时对话式 voice AI framework
  - 生态里已经有：
    - VAD
    - turn detection
    - realtime speech assistant 示例
- 最值得我们借鉴的点：
  - 语音交互链条工程化较成熟
  - 如果我们后面想快速做一版“实时对话入口”，可借鉴其 runtime 组织方式
- 当前结论：
  - 和 Pipecat 类似，**更像实时语音层候选**
  - 不适合作为整个 ClawSense / OpenClaw 记忆层底座

### 2.5 Vexa

- 仓库：
  - [Vexa-ai/vexa](https://github.com/Vexa-ai/vexa)
- 为什么重要：
  - 它不是旧手机感知路线，而是“会议 bot 路线”
  - 能自动加入 Zoom / Teams / Meet，拿到实时 transcript、chat、screen
- 最值得我们借鉴的点：
  - 如果以后要覆盖：
    - 远程会议
    - 人不在场时的会议代理
    - 云端会议 transcript 管道
  - 它会非常有参考价值
- 当前结论：
  - **不是当前第一优先**
  - 但对“办公打工人”来说，非常可能成为后续重要扩展入口

### 2.6 OpenAdapt Desktop

- 仓库：
  - [OpenAdaptAI/openadapt-desktop](https://github.com/OpenAdaptAI/openadapt-desktop)
- 为什么重要：
  - 它提供了一个很强的“采集 -> 审核 -> 上传”桌面侧工程模板
  - 其中最值得借鉴的不是助手能力，而是：
    - 录制控制
    - crash recovery
    - upload queue
    - storage tiering
    - PII scrubbing
- 当前结论：
  - **更适合借鉴桌面端工程能力**
  - 尤其适合 B 线未来做 Mac 客户端时使用

## 3. 哪些东西我们可以直接借

### 可直接借鉴的方向

1. screenpipe 的事件驱动屏幕采样思路
2. screenpipe 的 accessibility tree first 思路
3. Pipecat / TEN 的实时语音 runtime 思路
4. OpenAdapt 的 upload queue / review / scrub 工程思路

### 不建议直接整仓引入的

1. Omi
- 太完整，也太重
- 更适合借产品边界和数据模型

2. Vexa
- 很强，但它更偏“会议 bot 产品”
- 不是我们当前旧手机路线的主闭环

## 4. 对我们下一步的具体启发

### 对 A 线（实时拟人化助理）

最该借的是：

- Pipecat / TEN：
  - 解决“怎么实时说话、怎么 turn-taking、怎么做语音互动”
- Omi：
  - 解决“实时语音层最终该接成什么产品形态”

这意味着 A 线不要再被定义成：

- 晚上问答更好

而要定义成：

- **围绕 current context 的语音助手**
- 重点是：
  - 我现在看到了什么
  - 我现在听到了什么
  - 我现在该注意什么

### 对 B 线（Mac 客户端 / 数字世界感知终端）

最该借的是：

- screenpipe：
  - 屏幕事件模型
  - accessibility tree / OCR 组合
  - 事件驱动采样
- OpenAdapt：
  - 录制控制、上传队列、清理与审核

这意味着 B 线最好不要从“录屏工具”开始做，也不要把它做成独立平行产品，而要从：

- **统一客户端模型**
- **结构化 screen events**
- **screen evidence 进入同一记忆层**

开始做。

这里的关键产品约束应固定为：

- Mac 端和 Android 端都属于 ClawSense 客户端
- 二者共用：
  - 设备接入模型
  - 媒体库
  - 上传协议
  - evidence / retrieval / review
- Mac 端只是多了“屏幕”这一类数字世界采集能力
- 音频链路应尽量与 Android 端共用同一套 ingest 和 media/evidence 结构

## 5. 当前建议

当前最合理的推进方式是：

1. A 线先继续作为主线
- 但要按“current context + voice interaction”重定义

2. B 线先进入技术预研
- 优先调研和验证：
  - screenpipe 哪些模块或思想可直接借
  - 是否需要自研 Mac capture agent，还是先做 sidecar 集成

3. 不建议现在就直接全面接入某个大项目
- 更适合：
  - 借思路
  - 借数据模型
  - 借事件采样策略
  - 借 realtime runtime 组织方式
